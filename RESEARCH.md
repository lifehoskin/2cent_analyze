# Исследование лимитных заявок: сбор и подписанные ордера, 17 сентября 2026

## Исправление смешивания WebSocket-потоков — 3 октября 2026

При восстановлении `research-cases-20261003-044526.zip` обнаружена ошибка:
multi-token `price_change` может приходить через оба соединения, если исходы
рынка распределены по разным сокетам. Ранее обе копии применялись к обоим
стаканам. Запоздалая копия возвращала старые размеры и создавала ложные изменения
уровней. В 13 окнах было 213 094 отката source timestamp при обновлении токена;
после восстановления каждого токена только по его собственному соединению — 0.
59 отдельных сравнений токена с прежним checkpoint дали расхождение.

Теперь BookFeed передаёт принадлежность токенов соединению, а MarketCapture
применяет только принадлежащие ему book/price_change/tick_size_change. Сырые
пакеты price_change сохраняются целиком, в том числе повторы: данные остаются
проверяемыми. Не применяется дедупликация только по timestamp — разные изменения
в одной миллисекунде допустимы. После reset дельта не заменяет полный снимок.
`capture_start.version=2`, политика `connection_owned_assets`; checkpoint
добавляет source_connection_id для каждого токена. Схема SQLite не меняется.

Для старых v1 данных: восстановить владельцев подписок из subscribe/unsubscribe
в capture-metadata; начать с реального full book собственного соединения;
старые checkpoint и quote_observations не использовать как исправленную истину.
Файл research-cases сохраняет необходимые полные сырые кадры, поэтому часть
старых данных можно пересчитать без нового сбора. Это не восстанавливает
рынки, которые вообще не были подписаны.

Гипотеза повторного котирования сохранилась после исправления: 22 доступным
подписанным заявкам соответствуют прибавления полного размера через 40–150 мс
по меткам client/source. Это ассоциация, не доказанная задержка биржи. За 10
минут до восьми входов по 2¢ найдены 75 пар −1000/+1000 с паузой ≤30 секунд
без reset и без принта 2¢/98¢ в пределах ±1 секунды от снятия. Их владелец
публично неизвестен; отсутствие принта не доказывает отмену.

Регрессия воспроизводит запоздалый дубль через второй сокет, проверяет
неизменность быстрого стакана, целый raw payload, разные события с одинаковым
timestamp, provenance checkpoint и снятие подписки.

После `git pull --ff-only` перезапустить `npm run pm`. Процесс `pm:orders`
не требует перезапуска из-за этого исправления. Старые базы сохранять; новые
сессии отмечены версией 2. Discovery/capacity требуют отдельного улучшения.

## Адресный экспорт стаканов — 3 октября 2026

После overview можно выгрузить нужные окна непосредственно из `data/`:

```bash
python3 research_cases.py --db data --overview research-overview-20261002-203026.zip
```

Для этого конкретного overview выбираются 13 рынков, 32 подписанные заявки:
все рынки, где есть хотя бы один сохранённый контекст создания, включая рынки
только с контекстом продажи. У 22 из этих заявок есть контекст; выборка не
представляет все рынки/все незаполненные ордера и не доказывает прибыльность.
Оба исхода, 15 минут до самого раннего создания и 15 минут после последнего
наблюдаемого исполнения на рынке. Дополнительные 120 секунд нужны для загрузки
начального стакана; отсутствие снимка остаётся пробелом, а не нулевой глубиной.

Результат — один `research-cases-YYYYMMDD-HHMMSS.zip`, без промежуточного полного
экспорта. Исходные базы открываются только для чтения. Сохраняются все релевантные
кадры внутри окон, включая публичные принты и целые пакеты изменений обоих
исходов, reset и checkpoint. Checkpoint сокращён до пары выбранных токенов;
пустой checkpoint тоже сохраняется и инвалидирует прежнее состояние. Каждое
окно и сессия воспроизводятся отдельно. Не связывать стаканы через reset.

`--before`, `--after`, `--warmup` задаются в секундах. `--selection path.json`
позволяет передать явный `{"cases":[...]}` с condition_id, asset_ids (2 токена),
slug, since/until (ISO с часовым поясом), в том числе контрольные окна.
Нужны исходные дневные базы и overview ZIP. Размер итогового ZIP заранее не
гарантируется; он зависит от активности выбранных рынков. Скрипт печатает прогресс.

`research_export.py` теперь сохраняет запрошенный диапазон дат и явно предупреждает
об отсутствующих дневных базах. В overview от 2 октября фактический журнал
заканчивается 30 сентября 17:09:48 UTC; отсутствие файлов за 1–2 октября не
доказывает причину остановки. Дата имени ZIP — время экспорта, не последней сделки.

Проверки: `python3 test_research_cases.py`, `python3 test_research.py`.
Изменений live-подписок/лимитов сбора в этом дополнении нет: сначала нужно
отдельно устранить пропуски discovery и capacity и проверить часы сборщика.

## Компактный экспорт для первой проверки — 2 октября 2026

Сначала отправлять обзорный пакет, не создавая полный многогигабайтный экспорт:

```bash
python3 research_export.py --db data --since 2026-09-27 --until 2026-10-02 --overview
```

Команда создаёт папку и `research-overview-YYYYMMDD-HHMMSS.zip`. Даты UTC,
обе границы включены; дата конца может быть текущим неполным днём.
Режим включает сделки, подписанные ордера и их контекст при наличии order DB,
реестры рынков, причины подписки, сбросы и размеры/временные границы исходного
журнала. Он не копирует все кадры стакана, публичные принты и quote_observations.
Счётчики событий в manifest относятся к исходным базам, а не к содержимому ZIP.
Исходные базы открываются только для чтения; работающий сбор можно не останавливать.
Снимок каждой базы согласован отдельно, общий момент фиксации всех баз не обещается.

Загрузить сначала этот ZIP. Сохранить `data/`: overview не является резервной
копией и не позволяет восстановить последовательность снятия/возврата заявок.
После проверки покрытия можно выбрать рынки для полного исследования.
Без `--overview` команда по-прежнему создаёт полный экспорт.
Если есть WARNING об отсутствии order database, в пакете не будет подписанных
ордеров; предупреждение нужно прислать вместе с архивом.

## Обновление 19 сентября: непрерывность и честный журнал покрытия

В полном журнале трёх рынков найдены повторные изменения ±1000 долей на 2¢.
Последние +1000 согласуются со временем трёх подписанных заявок в пределах
39–51 мс по часам источника. Это сильная ассоциация последней заявки, но более
ранние изменения остаются анонимными кандидатами; L2 не раскрывает владельца.
Клиентские часы, часы WebSocket и блока нельзя считать одним точным таймером.

Исправления сборщика:

- WebSocket изменяет подписки через subscribe/unsubscribe на существующих
  соединениях. Добавление рынка больше не переподключает все остальные.
  Реальный разрыв по-прежнему инвалидирует стаканы до нового полного снимка.
  Запоздалые снимки уже отписанных токенов игнорируются; дельты без книги не
  восстанавливают её. Формат динамических подписок проверен по официальной
  документации: https://docs.polymarket.com/market-data/realtime-data.
- Опрос рыночных сделок выделен из опроса кошельков, исключено наложение двух
  проходов. Первыми идут рынки, которые дольше не опрашивались, с приоритетом
  свежей активности среди ещё не опрошенных. Длинный проход не застревает на
  первых 25 старых рынках.
- В сыром журнале появились `schedule_decision`: conditionId, status, source,
  subscribeAt, holdUntil, gameStart, subscribedAt, releasedAt. Запись только при
  изменении. Причины включают ожидание окна, capacity и окончание окна без
  подписки. `universe.subscribed` теперь означает хотя бы одну фактическую
  подписку планировщика; здоровье соединения проверяется по reset/snapshot.
- Экспорт отделяет повторно полученную API-историю за другие даты в
  `historical-target-fills.csv`. `target-fills.csv` содержит только даты выбранных
  UTC-файлов. `chain-fills.csv` остаётся основой для точного подсчёта событий.

Старые данные не исправляются задним числом. Ограничение discovery первыми
страницами новых рынков и лимит 150 рынков на спорт сохраняются: отсутствие
записи не доказывает отсутствие заявки бота. Новые причины нужны, чтобы измерить
пропуски до расширения охвата. Парный стакан может отражать ту же ликвидность
через 1−p; это не независимый источник справедливой цены.

новые таблицы добавляются при открытии дневной базы. Полный журнал появится
только после обновления: восстановить пропущенные старым сборщиком события нельзя.

В `pm.config.json` включён `capture.enabled`, контрольный снимок — раз в 60 секунд.

`0xd403596d8690210994e7f4bae6b9dac1b7e4a817`,

предматчевой контекст; это не обнаруженный параметр стратегии бота.

## Время создания подписанных ордеров

После обновления держать **два терминала** в папке проекта:

```bash
# Терминал 1: непрерывный стакан
npm run pm
```

```bash
# Терминал 2: исполненные подписанные заявки из блокчейна
npm run pm:orders
```

На Mac можно обернуть каждую команду в `caffeinate -i`. Сначала остановить старый
процесс Ctrl+C и обновить ветку. Новых npm/pip зависимостей нет; проверено на
Node.js 24 и Python 3.12. Второй процесс читает `wallets`/`trades` дневных баз,
получает input, receipt и заголовок блока из публичных Polygon RPC. Никаких
ключей, подписи и торговых вызовов. Он пишет **отдельно** `data/order-research.sqlite`.

Первый проход обрабатывает до 100 транзакций; режим watch повторяет проход после
60 секунд и постепенно разбирает старую историю. Новые транзакции имеют приоритет
перед повторными ошибками. Ошибки повторяются не раньше чем через 5 минут.
`[orders] decoded / error / pending` показывает результат прохода. Архивный RPC
может временно не отвечать; это остаётся в журнале ошибок, а не исключается молча.

Для сбора только новой истории:

```bash
npm run pm:orders -- --since 2026-09-17
```

Дата фильтрует **время самих сделок**, включая историю, повторно записанную API в
новый дневной файл. Для разового импорта известного CSV с `tx_hash`:

```bash
python3 order_research.py --from-csv order-ages.csv --limit 3000
```

Это обогащение только известных хешей; CSV из прежнего исследования не содержит
98 исключённых транзакций. Самостоятельное полное исследование использует все
покупки из API, а не только эти строки. Получение input доступно лишь для
исполненных ордеров; незалитые отменённые заявки так не найти.

В новом research-export автоматически появляются `chain-fills.csv`,
`signed-orders.csv`, `counterparty-fills.csv`, `order-creation-context.csv`,
`chain-rpc.jsonl.gz` и `order-errors.csv`. Идентичность исполнения —
chain/tx/log_index, заявки — chain/exchange/order_hash. В одной транзакции может
быть несколько заявок одного адреса по разным уровням. Все сохраняются, тейкер
учитывается один раз по агрегатному событию. Поддержан прямой `matchOrders` V2
двух официальных exchange-контрактов; неизвестный формат — явная ошибка.

`client_created_utc` — время, указанное клиентом в подписанном ордере.
Это **не подтверждение приёма биржей**. Разница с временем блока включает
расхождение часов и задержку расчёта. Она не равна частоте перестановки.
Первый филл и накопленный объём означают «наблюдались в этом экспорте».
Неисполненный остаток не означает, что заявка до сих пор стоит в стакане.

Контекст берётся до client timestamp минус 60/10/1/0 секунд из собственного
журнала. Для каждой точки есть статус и возраст образца/источника. Пропуск,
reset, пересечённый стакан и старый образец не подменяются нулями. Разность
часов клиента и сборщика неизвестна: даже доступный контекст требует проверки
чувствительности к сдвигу времени. Восстановить книгу прошлых месяцев, если она
не записывалась, новый модуль не может. Владелец анонимного уровня не назначается.

ITF и MLB теперь **явно включены** в `disciplines`: без этого предшествующий
контекст их первых покупок отсутствует. `labels` остаётся отдельной картой,
Setka автоматически не включается. Сохраняется потолок 150 live-рынков на спорт
(ITF делит бюджет с остальным теннисом; приоритетные рынки кошельков могут его
превысить). Это увеличивает охват и расход диска; лимит не гарантирует, что
каждый нужный рынок будет подписан заранее.

## Что собирать и отправлять

Для первой проверки достаточно 6–12 часов активных матчей; затем нужны несколько
дней с реальными исполнениями. Сначала проверить, есть ли контекст **до** новых
филлов нужного кошелька. Количество часов само по себе не гарантирует выборку.

Компактный архив, как раньше:

```bash
python3 export.py --db data
```

Новый непрерывный архив для выбранных UTC-суток:

```bash
python3 research_export.py --db data --since 2026-09-16 --until 2026-09-16
```

Обе даты включены; заменить их на реальные даты сбора. Без `--until` берутся
все дневные файлы начиная с `--since`. Команда напечатает путь
`research-export-<время>.zip`; внутри сжатые JSONL/CSV, README и manifest с
числом строк и фактическим периодом. Передать этот ZIP вместе с `export.zip`.
Чтение не останавливает сборщик, но экспорт активного дня отражает только
снимок базы на момент запуска. Полный журнал занимает больше места; для первой
проверки отправлять один день. Старые SQLite-файлы не удаляются и не сокращаются.

## Что изменилось

- `market_events` сохраняет все распознанные сообщения рыночного WebSocket:
  полный стакан, изменения уровней, `last_trade_price`, смену тика и другие
  события. Сохраняются исходные поля, время приёма, монотонное время процесса,
  идентификаторы сессии/соединения и последовательность. Это распарсенные
  сообщения JSON, не побайтовая запись сетевых кадров; PING/PONG не сохраняются.
- `quote_observations` фиксирует bid/ask обоих исходов **после всего кадра**,
  часы источника, пересечённость книг, bid/ask объём на .01/.011/.02/.03/.05
  и .25/.40/.50/.70/.81/.85/.90, объём и стоимость бидов строго выше уровня.
  Это совокупная видимая ликвидность, а не точная очередь конкретной заявки.
- Раз в минуту и при смене UTC-файла пишется полный контрольный снимок. При
  реконнекте старый стакан сбрасывается; дельты до нового полного снимка не
  считаются достоверным состоянием. Обе стороны рынка могут быть на разных
  соединениях: их часы по-прежнему нужно сравнивать.
- Экспорт и PnL убирают повторы сделок между суточными файлами. Идентичность:
  tx_hash + wallet + asset + side + size + price. Без tx_hash запись не склеивается.
  API без log_index не позволяет разделить одинаковые исполнения внутри одной
  транзакции. Позиции и счётчики разделены по кошелькам.
- `book-series.csv` теперь резервирует 75% окон для падений до 5¢ и ниже,
  остальные — для более высоких цен, с выборкой по дням. Неиспользованные места
  перераспределяются. Раньше ранжирование по удалённому объёму почти вытесняло
  дешёвые свипы. Непрерывный research-export вообще не делает такой выборки.

## Следующий анализ

1. Проверить покрытие: исполнение попало в подписанный интервал, есть полный
   снимок и обновления до него, отсутствуют разрывы. Отдельно учитывать рынки,
   которые начали наблюдать только после первой сделки кошелька.
2. Восстановить уровни **до** исполнения и появления кандидата в заявку.
   Проверять лестницу .90 → .85 → .81 → .70 → .50 → .40 → .25 и дешёвые уровни
   .011/.02; объёмы 200/300/400/500/600/1000 и меняющиеся дешёвые объёмы считать
   гипотезами, а не правилом поиска, исключающим все другие варианты.
3. Сопоставить исчезновение ликвидности с рыночными принтами и подтверждёнными
   филлами кошелька. Без подтверждения это изменение уровня, не доказанный свип
   маркет-ордером и не доказанная отмена лимитки.
4. Сравнить с наблюдавшимися рынками без филла: вид спорта, тип/сегмент рынка,
   время до старта, spread, глубина над ценой заявки, недавние принты,
   волатильность, частота изменений и одинаковые размеры уровней.
   Минутные checkpoint-наблюдения дают контрольные моменты независимо от исхода;
   отсутствие филла не означает отсутствие заявки.
5. Проверять отдельно выбор рынка, цену и размер заявки. Разделять обучение и
   проверку по матчам и датам, сравнивать с простой постоянной лестницей,
   не использовать будущую победу/отскок в признаках принятия решения.

`1 - paired_ask` часто зеркалит bid того же рынка. Он не является независимой
«справедливой вероятностью». У прежних записей добавлялась проблема расчёта
парной метрики между двумя изменениями одного кадра. Старые значения не
пересчитываются без исходного потока; новые позволяют проверить это явно.

## Проверки разработки

```bash
npm run test:pm
```

Запускает все тесты модулей Polymarket и пять Python-наборов, включая реальную
SQLite → экспорт → чтение архива цепочку. Live-соединение с Polymarket и
многосуточная нагрузка должны проверяться на машине сбора.
